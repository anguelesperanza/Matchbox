# Adding 3D to Matchbox

## Why

Two games exist and neither can be rebuilt here.

`CoffeeGame` is first person, built out of coloured cubes, a ground plane and a
grid, with Box3D resolving collisions and a hand that picks things up by casting
a ray. It draws nothing that is not a box.

`PsxGame` is first person over loaded `.gltf` models, lit by
a single flickering point light with distance fog, rendered into a texture and
then put through a full-screen shader that quantises it to 15-bit colour, dithers
it and draws scanlines. A second shader does a VHS wobble. The look *is* the
game.

Both are raylib. Matchbox has no 3D of any kind, so there is nothing to port them
onto. This is the plan for that.

## What Matchbox is today, and why none of it helps

Worth stating plainly, because the shape of the existing renderer decides most of
what follows.

Every draw in Matchbox is the same unit quad. One vertex shader
(`shaders/quad.vert.hlsl`) reads a 48-byte uniform block, scales that quad by
`size`, rotates it, places it at `position` and divides by the screen dimensions.
Sprites, rectangles, outlines, glyphs and shapes differ only in which fragment
shader runs and what is in the fragment uniform block. There is exactly one
vertex buffer in the whole program and it is four vertices long.

That design is why 2D is fast and why 3D is a genuine addition rather than a
tweak:

- **no per-object geometry.** A model is vertices, and nothing in the renderer
  can hold any
- **no depth.** Render passes are colour-only, and draw order is the only thing
  deciding what covers what
- **no matrices.** The vertex shader does screen-space arithmetic, not a
  transform chain
- **no render targets.** `examples/framebuffer` is a `Pixel_Buffer`, which is CPU
  pixels uploaded to a sampled texture. It is not something the GPU draws into
- **`Mesh` is already taken.** It is the texture holder that `Sprite` embeds with
  `using`
- **`matchbox/gltf2/` is vendored and referenced nowhere.** Groundwork someone
  laid and never used. It is the loader this plan uses

Two smaller things that do help. `mbi.input.mouse_dx/mouse_dy` already accumulate
`xrel`/`yrel` off `MOUSE_MOTION` every frame, so mouse look needs an accessor
rather than an implementation. And `clear_background` already ends a pass and
opens a new one mid-frame, so the machinery for switching passes exists and is
proven.

## Goal

`CoffeeGame` and `PsxGame` both rebuilt on Matchbox and looking as they do now.

Behaving as they do now, with one deliberate exception. `PsxGame` moves onto a
solver (D7), and a capsule against a broadphase does not slide the way three
reverted axes do -- narrow gaps and shallow corners will feel different. That is
not a regression to be chased back to parity. It is what drawing the line costs,
and it is accepted here so that nobody spends a week in stage 6 trying to make a
solver reproduce an approximation of one.

Nothing in the 2D path changes behaviour, and a game that draws no 3D allocates
no depth buffer and pays nothing.

## Scope

**In.** A depth buffer and a 3D render pass. A `Camera3D` and first-person mouse
look. Generated primitives -- cube, plane, sphere, grid -- and wireframes. Static
`.gltf` models with textures. A built-in lit shader with point lights and
distance fog. Render targets. PSX and VHS post-processing.

**Out.** Collision detection, ray casting and physics of every kind -- see the
next section and D7. Skeletal animation, PBR, shadow maps, instancing, MSAA. A
shader API for games (see D3). Each is noted at the end with what it would take.

## The line Matchbox draws

Matchbox is a rendering and input framework. It carries enough to draw things,
to read what the player did, and to handle the basic interactions between those
two -- is the pointer over this, which way is the camera facing. Anything past
that belongs to a library that does it for a living.

Physics is the first place 3D pushes against that line, and it is settled here
rather than discovered later: collision detection, ray casting against a world,
and resolving movement all go to Box3D, which Odin ships bindings for. See D7.

The rule that follows, and it matters more than it looks: **Matchbox does not
import `vendor:box3d`.** A 2D card game must not acquire a physics library
because 3D exists. The framework hands out positions, directions and dimensions
as plain vectors; the game hands those to Box3D itself.

## Decisions

Ten, in rough order of how much else depends on them. D2 is the one that will
silently ruin a day.

### D1. 3D is a second render pass, not a change to the first

SDL3 bakes target formats into the pipeline object at creation. The five existing
pipelines declare one colour target and no depth-stencil target, and a pipeline
whose `target_info` disagrees with the pass it is used in is invalid.

So there are two ways to get depth. Give every existing pipeline a
`depth_stencil_format` and turn depth testing off in the 2D ones -- which
recreates all five and makes a pure-2D game carry an 8MB depth buffer at 1080p
for nothing. Or open a separate pass.

Separate pass. `begin_drawing_3d` ends whatever pass is open and starts one with
a depth attachment cleared to 1.0; `end_drawing_3d` ends that one, and the next 2D
draw opens a colour-only `LOAD` pass through the `ensure_pass` that already
exists. A frame is then two or three passes instead of one, which is nothing.

The cost worth knowing: alternating 3D and 2D repeatedly in one frame pays a pass
switch each time. The shape both games use -- scene, then HUD -- pays it once.

### D2. Matchbox writes its own projection matrices

**This is the one that fails silently.** `core:math/linalg` has
`matrix4_perspective`, and it is the wrong matrix:

```odin
m[2, 2] = +(far + near) / (far - near)
m[2, 3] = -2*far*near / (far - near)
```

That is the OpenGL convention, mapping the view frustum to clip z in `[-1, 1]`.
SDL3_GPU normalises to the D3D convention on every backend, where clip z runs
`[0, 1]` -- the same reason `quad.vert.hlsl` negates y with a comment about it.
Feed it a GL matrix and everything from the near plane to the midpoint of the
frustum lands at negative z and is clipped away. What you see is a scene where
close things vanish and distant things depth-test against each other wrongly,
which reads as "my model isn't loading" and sends you looking in the wrong place
for a day.

So `matchbox/math3d.odin` gets `perspective`, `ortho` and `look_at` written here
with a `[0, 1]` depth range. `linalg`'s vector and matrix *types* and its
quaternion helpers are fine and used throughout -- it is only the projection that
carries a convention.

Related, and cheaper: 3D does **not** negate y. World +y is up, the projection
handles it, and only the 2D shader flips because Matchbox measures 2D from the
top-left.

### D3. Game shaders are ported to HLSL and shipped as Matchbox pipelines

`lighting.vs`/`lighting.fs`, `psx.fs` and `vhs.fs` get rewritten as HLSL in
`matchbox/shaders/`, compiled by `build_shaders.bat` alongside everything else,
and loaded by `init` into the `Shaders` and `Pipelines` structs like the other
six.

There is no runtime shader loading, no `load_shader(vert, frag)`, no uniform
declaration API, and no reason for anyone building a game to have `dxc`
installed.

The consequence to accept: an effect is a parameter, not code. A game that wants
a look Matchbox does not ship asks for a new built-in rather than writing one.
Everything still goes through `create_pipeline`, so opening that door later is
additive -- but it is not this plan.

### D4. Post-processing reuses the quad

`psx.fs` and `vhs.fs` are fragment-only. The existing quad vertex shader already
draws a screen-space rectangle of arbitrary size at an arbitrary place. A
full-screen effect is therefore one ordinary quad draw with `size = screen`,
sampling the render target, with the PSX or VHS fragment shader bound.

Which means post-processing costs a fragment shader and a uniform block each and
touches nothing else. This is the part of the port that is nearly free, and it is
why D3 works out. What resolution it runs at is D9.

### D5. Render targets use the swapchain's format

A target created in some other format needs its own copy of every pipeline that
draws into it, because of D1's rule about baked formats. Created in
`GetGPUSwapchainTextureFormat`, every pipeline that already exists stays valid
inside an offscreen pass -- including all the 2D ones, so a game can draw a
sprite or a line of text into a render target on the way past.

### D6. The 3D types are `Model` and `Model_Part`

`Mesh` is the 2D texture holder and `Sprite` embeds it with `using`, so renaming
it reaches through the entire 2D API for no gain. A `Model` is what a file loads
into: a slice of `Model_Part`, each holding a vertex buffer, an index buffer, a
material and a local bounding box, plus the whole model's bounds.

### D7. Collision and physics are Box3D's, not Matchbox's

Matchbox provides **no** bounding boxes, no overlap tests and no ray casts. Not a
thin maths layer either. Games use Box3D.

The two games arrived at this from opposite directions, which is what makes the
answer clear.

`CoffeeGame` already owns a Box3D world. Collisions come out of `World_Step`,
picking things up is `World_CastRayClosest`, and placing them again uses the
surface normal that cast returns. It asks Matchbox for none of it.

`PsxGame` hand-rolls four things against raylib's helpers, and **every one of
them has a Box3D counterpart that `CoffeeGame` is already using**:

| `PsxGame` today | Box3D |
|---|---|
| `get_transformed_bounding_box` (`src/main.odin:68`) -- model box, scaled, moved to world space | `Shape_GetAABB` / `Body_ComputeAABB`, off the body that already knows where it is |
| `get_player_bounding_box` (`src/main.odin:120`) -- an AABB around the camera | a capsule on a dynamic body with rotation locked, exactly as `make_player` does |
| `collision` (`src/main.odin:140`) -- move-and-slide, one axis at a time | `World_Step`, which slides along walls because that is what a solver does |
| `GetRayCollisionBox` (`src/main.odin:296`) -- what am I looking at | `World_CastRayClosest`, which also returns the normal and the shape it hit |

So porting `PsxGame` means deleting those four and modelling its world on
`CoffeeGame`'s. That is work in the game, not in the framework, and it replaces
per-item AABB tests with a broadphase that will hold up when the scene stops
being five boxes.

**What Matchbox still owes, and why each is rendering rather than physics**

- **a model's own bounds**, as a field on `Model` filled in at load while the
  vertex data is in hand. It is a property of the asset, and it is what a game
  reads to size a `MakeBoxHull` for the model it just loaded. Without it every
  game re-walks the vertices to learn something the loader already knew
- **`draw_box_wires(centre, size, colour)`**, which is what replaces
  `rl.DrawBoundingBox`. Plain vectors in, no Box3D types, so a game turns a
  `b3.AABB` into a centre and a size in two lines and Matchbox stays ignorant of
  the library
- **`camera_forward(camera) -> [3]f32`**. Both games need it and neither needs it
  for physics: `CoffeeGame` walks along it and `PsxGame` looks along it. It is
  the direction the camera faces, which is camera maths

Note what is *not* in that list: a `Ray` type. `World_CastRayClosest` takes an
origin and a translation as two arguments, and a game already holds the origin
(`camera.position`) and can multiply the forward vector by a reach. A `Ray`
struct would exist only to be taken apart again.

The same reasoning applies backwards to 2D, and explains why `collisions.odin`
being nearly empty was never the omission it looked like. Odin ships `box2d`
too.

### D8. Models are static `.gltf` only

`matchbox/gltf2/` already parses the format. Skinning, joints and animation
sampling are deferred, because neither game needs them.

### D9. The low-resolution look stays in the fragment shader

`psx.fs` samples a full-resolution texture on a 320x240 grid rather than being
drawn at 320x240. Ported as it is.

The alternative -- a render target at native low resolution, upscaled -- shades
far fewer pixels and would give real vertex wobble and affine warping instead of
an imitation of them. It also means rewriting the effect shaders rather than
translating them, and it changes what the game looks like. Not what this plan is
for.

`Render_Target` takes a size regardless, so the day that is worth trying it is a
change to one line in the game and not to Matchbox.

### D10. `begin_drawing_3d`, not `begin_mode_3d`

Matchbox already has `begin_drawing_2d` / `end_drawing_2d` for its 2D camera, so
raylib's `BeginMode3D` would put two conventions in one API for the sake of
matching a framework the game is being ported *away* from.

The types stay `Camera` and `Camera3D`, which is the one asymmetry left standing.
Renaming `Camera` to `Camera2D` would be tidier and would break every game
already using it, which is not a trade worth making for symmetry.

## Stages

Each one ends somewhere you can see it working.

### Stage 1 -- Depth, a 3D pipeline, one cube on screen

The stage that proves D1 and D2, and the one where a mistake is cheapest to find.

**Work**

- `matchbox/math3d.odin`: `perspective`, `ortho`, `look_at`, `Transform`
  (position/rotation/scale to a `matrix[4,4]f32`)
- `matchbox/render3d.odin`: a depth texture created lazily on first
  `begin_drawing_3d` and recreated when the window size changes. Format chosen by
  asking `GPUTextureSupportsFormat`: `D24_UNORM_S8_UINT`, else `D32_FLOAT`, else
  `D16_UNORM`
- `Vertex3D :: struct { pos: [3]f32, normal: [3]f32, uv: [2]f32 }` -- 32 bytes
- `mesh.vert.hlsl` / `mesh_flat.frag.hlsl`: MVP, model matrix and normal matrix
  in the vertex uniform block, flat colour out
- `create_pipeline` grows parameters. It currently hardcodes
  `shaders.quad` and the two-attribute layout; it needs the vertex shader, the
  vertex layout, the depth-stencil state and the cull mode passed in. The five
  existing calls keep their current behaviour
- `begin_drawing_3d(camera)` / `end_drawing_3d()`
- `upload_mesh(vertices, indices) -> Model_Part` on the existing `upload_buffer`
  staging path
- a cube generated in code, and `draw_model(model, transform, tint)`

**Done when** `examples/cube` shows a spinning coloured cube that a second cube
correctly passes behind, with 2D text drawn over the top afterwards. The text
proves the pass switch in D1; the cube passing behind proves depth; a near cube
staying visible proves D2.

**Done. What running it changed:**

- **D2 is confirmed by experiment, not by argument.** linalg's projection was
  swapped in on purpose to watch it fail: the cube 0.15 units from the eye
  disappears and the other three carry on looking entirely reasonable. No error
  and nothing logged, which is the failure mode the decision claimed
- **`enable_depth_clip` has to be set, and its zero value is the wrong one.**
  SDL3 reads the field as written -- false means depth *clamp*, so geometry
  outside the near and far planes is squashed onto them and drawn instead of
  discarded. The first attempt at the D2 experiment failed to reproduce anything
  because of it: a near plane that does not cut hides the bug the near cube
  exists to catch. Two silent failures on top of each other, and the second was
  only visible because the first was being deliberately provoked
- **`camera3d_forward` and `camera3d_right` arrived a stage early.** Stage 2
  lists them, but placing the near-plane cube in world coordinates put it
  outside the frustum, and placing it off the camera's own basis is both correct
  and the thing a game would do
- **The fixed light in `mesh_flat.frag` earns its place.** A cube in one flat
  colour is an unreadable hexagon and a rotating one looks static. Stage 5 still
  replaces it
- depth format on this machine is `D24_UNORM_S8_UINT`, drawn on screen by the
  example because it is the number most likely to differ on Android

### Stage 2 -- A camera you can walk with

**Work**

- `Camera3D :: struct { position, target, up: [3]f32, fov: f32, projection: enum
  { PERSPECTIVE, ORTHOGRAPHIC } }`, matching what both games already fill in
- `get_mouse_delta() -> [2]f32`, exposing the `mouse_dx/mouse_dy` that
  `poll_events` has been accumulating all along
- `set_cursor_locked(bool)` / `cursor_locked()` over
  `SDL_SetWindowRelativeMouseMode`, which is raylib's `DisableCursor`
- `camera_first_person(&camera, &yaw, &pitch, speed, dt)` -- the WASD and
  yaw/pitch block both games write out longhand, pitch clamped just short of
  vertical
- `camera_forward(camera) -> [3]f32` -- what the camera faces. `CoffeeGame`
  walks along it, `PsxGame` casts along it, and Box3D takes it as the
  `translation` argument once multiplied by a reach (D7)

**Done when** `examples/first-person` walks around the stage 1 cubes with the
mouse captured and ESC releasing it.

**Done, and verified by driving it rather than by looking at it.** Synthetic
input: holding W for 1.2s moved the camera 7.3 units at a speed of 6, which is
the right answer; 25 steps of horizontal motion turned yaw from -1.57 to -0.45
and moved the position not at all; pitch clamps at exactly ±1.56 at both ends
with no roll-over; one ESC released the pointer and left the window running, a
second closed it.

**What changed from the plan:**

- **`camera3d_first_person` is the one a real game will not call.** It moves the
  camera itself, which is precisely what a game with a solver cannot allow. The
  useful thing is the three pieces underneath -- `camera3d_look` for the angles,
  `walk_direction` for what the keys are asking, `camera3d_aim` to point the
  camera after physics has moved it -- and the composite is a convenience for
  free cameras and examples. D7 is what forced the split, and the example
  carries the physics version in a comment
- **`camera3d_angles` was added.** Yaw and pitch live in the game, not on the
  camera, so a game starting them at zero snaps the view a quarter turn on frame
  one. This reads them back off a camera that is already pointed somewhere
- **`set_escape_key` turns out to be load-bearing.** Matchbox closes the window
  on ESC by default, and ESC is also how a first-person game gives the pointer
  back -- so every such game must call `set_escape_key(.UNKNOWN)` first. Worth
  knowing before it surprises somebody
- **`mouse_dx`/`mouse_dy` were documented as "pixels/dpi (inches)" and never
  were.** They are raw SDL relative motion, which is not the unit
  `get_mouse_position` is converted into. Corrected, since these two are public
  now: a number to multiply by a sensitivity, not one to add to a position

### Stage 2b -- The same camera, from behind

Not in the original plan, and it needed less than expected: a third-person
camera *is* the first-person one, pushed back along its own view direction. Same
yaw, same pitch, same `camera3d_look` producing both. What is added is a
distance and a character to point at.

**Work**

- `camera3d_zoom(&distance)` over the wheel `poll_events` already accumulates,
  clamped between `ORBIT_DISTANCE_MIN` and `ORBIT_DISTANCE_MAX`
- `camera3d_orbit_position(focus, yaw, pitch, distance, shoulder)` -- where the
  camera wants to be, as a plain vector and touching no camera
- `Camera3D_Shoulder :: enum { CENTER, LEFT, RIGHT }`, with `SHOULDER_OFFSET`,
  `camera3d_shoulder_amount`, `camera3d_side_offset` and `camera3d_orbit_focus`
  underneath it
- `camera3d_follow(&camera, focus, yaw, pitch, distance)` -- the third-person
  `camera3d_aim`
- `camera3d_orbit_angles(camera)` -- the third-person `camera3d_angles`, three
  numbers instead of two
- `camera3d_third_person(...)` -- the four of those in one
- `yaw_from_direction`, `turn_toward` and `facing_rotation`, which are what turn
  a character to face where it is running
- `Camera3D_Steering :: enum { CAMERA, CHARACTER }` -- whether turning the
  camera turns the run
- `Third_Person_Camera`, the lot of it in one struct, with
  `third_person_camera` to set it up and `third_person_input` /
  `third_person_follow` / `third_person_walk` to drive it

**Done when** `examples/third-person` walks the stage 3 blocks from behind, with
the character facing its own direction of travel, from either shoulder or from
directly behind.

**Done, and driven rather than looked at.** Holding W walks along -z at yaw
-1.57; thirty frames of horizontal motion turn yaw by 0.35 and the character's
facing follows it to within 0.01; pressing D swings the facing to 0.36, which is
`atan2` of the right vector for that yaw; one wheel notch takes the distance from
7.40 to 6.40; pitch clamps at exactly 0.30 and the camera stays 6.40 from the
focus throughout. `facing_rotation` was checked against
`direction_from_angles` through the same quaternion-to-matrix path `draw_model`
uses, at six angles.

The shoulders the same way. `camera3d_forward` is bit-identical across all three
settings, which is the claim the design rests on; the step is 0.75 at every
pitch from -1.3 to 0.3 and lies exactly along `camera3d_right`; the two
shoulders are opposite; the aim point stays `distance` from the camera, so the
wall cast still means what it meant. The character's own point, put through the
view matrix, lands at view-space x of -0.75 for `.RIGHT` and +0.75 for `.LEFT`
-- the camera steps one way and the character appears the other, which is the
part of the enum that is easy to write backwards. Driven in the example: W walks
the same -z through all three settings, with the character's x never leaving
zero.

**What it changed:**

- **`camera3d_look` grew a pitch range.** It clamped to `PITCH_LIMIT`, which is
  the right number for a head and the wrong one for an orbit: pitching up
  swings the camera *below* the character rather than tilting a neck, and the
  floor is a few degrees down. Two defaulted arguments, so nothing that called
  it before changed. `ORBIT_PITCH_MIN` and `ORBIT_PITCH_MAX` are deliberately
  asymmetric -- overhead is a view a game wants, underfoot is not
- **The composite is the useful one this time, which is the reverse of stage 2.**
  `camera3d_first_person` moves its camera and so a game with a solver cannot
  call it. `camera3d_third_person` has nothing to move -- the character is the
  game's, and the focus is an argument -- so it is correct with physics or
  without. The split still exists underneath, and exists for one thing:
  shortening the distance when something is between the camera and the
  character. That is a ray cast, which is Box3D's (D7), so
  `camera3d_orbit_position` hands over the point to cast at and stops there
- **`turn_toward` takes the difference across the wrap.** A character running
  east and turning north-east has a target that may be written 6.28 apart from
  where it is, and the naive subtraction spins it the long way round the
  compass. The example presses D at yaw -1.21 and the facing crosses pi rather
  than zero, which is the case that catches it
- **`facing_rotation` negates its yaw, and the sign is not obvious.** A rotation
  of `t` about +y takes +x to `{cos t, 0, -sin t}`, and the direction wanted is
  `{cos yaw, 0, sin yaw}` -- so it rotates by `-yaw`. On a symmetrical model the
  wrong sign looks fine until the character strafes
- the example keeps the camera off the floor by trigonometry rather than by a
  cast, and says so. It is behind a key so both halves can be seen: press C and
  look up, and the ground closes over the view

**Shoulders, and the one decision in them.**

Over the shoulder is the same rig slid sideways -- position and target together,
by the same vector -- rather than a camera turned to look past the character.
Turning is the obvious implementation and it is wrong: it points the camera away
from what the player is walking toward, so the thing you are heading for drifts
off the side of the screen as you approach it. Sliding leaves the view direction
untouched, which is why `walk_direction` needs no shoulder argument and why W
still goes the same way when you swap sides mid-stride.

- **The step is the camera's own right vector, and gets it for free.** For a
  camera with +y up, `cross(forward, up)` comes out as `{-sin(yaw), 0, cos(yaw)}`
  with the pitch cancelling out -- so a flat step by yaw alone *is* the right
  vector, and the offset does not shorten as the camera swings overhead
- **`SHOULDER_OFFSET` deliberately does not scale with distance.** It is a step
  to one side of the character, not a fraction of the frame, so pulling the
  camera in makes the framing more over-the-shoulder rather than less -- which
  is what a game does when it raises a weapon. The consequence is that the
  distance that suits the framing is the game's to pick, and the example picks
  it: 3.0 with a shoulder, back to whatever the wheel was left at when centred
- **The enum is a convenience over a signed f32, not the other way round.**
  `camera3d_shoulder_amount` gives the number and `camera3d_side_offset` turns
  it into the vector, because switching the enum snaps the view across the
  character and a game that wants the swap to slide has to interpolate
  something. It also means the enum is skippable entirely: add the offset to
  your own focus point and pass `.CENTER`, which is verified to produce the same
  rig
- **`camera.target` stops being the character**, which matters to exactly one
  caller: the wall-avoidance cast, which must start from `camera3d_orbit_focus`
  rather than from the character's centre or it casts along the wrong line.
  `camera3d_orbit_angles` reads the same aim point and so still round trips

**Steering, and the second thing a third-person camera has to decide.**

The first is where the camera sits, which is the shoulder. The second is whether
turning the camera turns the run, which is `Camera3D_Steering`.

- `.CAMERA` is what was there already: the keys are read against the camera, so
  W goes away from it and turning while walking curves the run, and the
  character is turned to face wherever it ends up going
- `.CHARACTER` reads them against the character's own heading instead. Look left
  while holding W and you carry straight on, looking left -- the camera swings
  round to watch from the side and the run does not notice
- `.STRAFE` reads them against the camera like `.CAMERA` does, but keeps the
  body facing the camera rather than facing its own direction of travel. A and D
  then side-step instead of turning into the step. Added later than the other
  two, when a game wanted it, and it is the setting `Camera3D_Shoulder` was
  really made for -- over the shoulder and strafing is the pair every
  third-person shooter offers

The implementation is two lines, because `walk_direction` already took a yaw and
the only question was which one to give it. What took the thinking was what
turns the character under `.CHARACTER`, and the answer is nothing: the rig does
not, on purpose, and turning is the game's -- `facing` is a plain field, and the
example spends two lines on Q and E to prove it. A game that wants free look as
a key you *hold* rather than a mode you are *in* puts the steering back to
`.CAMERA` on release and gets the MMO behaviour for free.

**Verified by driving all three.** Holding W with the mouse turning throughout:
under `.CAMERA`, yaw and facing move together from -1.29 to -0.69 and the path
curves; under `.CHARACTER`, yaw carries on from -0.69 to +0.21 while facing stays
pinned at -0.69 and the move vector stays exactly (0.774, -0.633) -- the same step
every frame, which is a straight line. Holding Q then walks the facing round and
the move vector with it, while the yaw goes on doing its own thing.

`.STRAFE` was driven against `.CAMERA` on the same input, which is the only way
to see what separates them. Forty frames of D from a standing start moves the
character the same 1.9 units sideways under both -- the keys are read the same --
but `.CAMERA` leaves the body at 1.57, a quarter turn, having swung to face where
it was going, where `.STRAFE` leaves it at 0.00, still facing forward. Then
turning the camera while standing still: `.CAMERA` leaves the body where it was,
`.STRAFE` brings it round to the camera's 0.77, and `.CHARACTER` leaves it at
0.00. Three settings, three different answers to the same two inputs.

- **The turn is not clamped to moving, unlike `.CAMERA`'s.** A character standing
  still under `.CAMERA` keeps the heading it had, because turning it would mean
  drifting round to face the camera for no reason. Under `.STRAFE` that drift is
  the whole feature: the body is facing where you are aiming, and aiming does not
  stop when the feet do
- **It turns at `turn_speed` rather than snapping**, so whipping the camera round
  leaves the body a moment behind. That lag is what stops a character looking
  welded to the lens; a game that wants it welded sets `turn_speed` high

**`Third_Person_Camera`, and where the line got drawn.**

Six numbers, a framing, a steering setting and a `Camera3D` all have to agree
every frame, and the example was carrying them as eight variables. They are one
struct now, built with `third_person_camera()` -- every argument defaulted, so
the short form is a working camera and the long form names only what differs.

- **The character's position is not in it.** That is the one field it would have
  been easy to add and wrong to: the position comes from the solver, so it is an
  argument to `third_person_follow` rather than a field somebody has to remember
  to write. D7 holds
- **Which is also why the frame is two calls and not one.** The character moves
  *between* reading the input and seating the camera, so `third_person_input`
  writes `move` and stops, and `third_person_follow` takes the position that
  came back out of the solver. `third_person_walk` is the two of them with the
  move in the middle, for a character nothing else drives -- the same role
  `camera3d_first_person` plays, and the same warning on it
- **`yaw` is not a constructor argument**, it is seeded from `facing`. Starting
  them apart puts the camera beside the character instead of behind it, which is
  the stage 2 lesson one step earlier
- the constructor seats the camera before it returns, so `rig.camera` is valid
  on the frame it was made rather than on the frame after
- the loose procedures are untouched and still the right thing for a game that
  keeps its own yaw and pitch. The struct is made of them, and the example
  reaches past it exactly once -- `camera3d_follow` again, at a shorter
  distance, when the floor is in the way

**Verified:** the constructor's defaults, its clamping of out-of-range distance
and pitch, and that a rig seats the camera at the same position and target the
loose procedures produce for the same numbers -- shoulder included. Driven in
the example, the floor clamp still holds the camera at exactly 0.40 through the
struct, and correctly does nothing at the closer over-the-shoulder distance where
the camera never reaches the ground.

### Stage 3 -- Primitives, wires and a grid

Everything `CoffeeGame` draws.

**Work**

- generated meshes: `cube_mesh`, `plane_mesh`, `sphere_mesh`, each with correct
  normals and UVs
- `draw_cube(position, size, color)`, `draw_plane`, `draw_sphere` -- immediate
  helpers over a shared generated mesh, which is what `rl.DrawCube` is
- a line pipeline: `.LINELIST` primitive type, no cull, depth test on. Used by
  `draw_cube_wires`, `draw_box_wires(centre, size, colour)` and
  `draw_grid(slices, spacing)`. `draw_box_wires` is what a game points at a
  Box3D AABB to see it (D7)

**Stage 3 done.** `examples/primitives` draws all of it: boxes with black
wireframes over them, a ground plane, a grid, two spheres, and one red outline
given by its corners rather than its centre.

**What running it changed:**

- **`enable_depth_bias` does nothing to lines, and this cost the most time in
  the stage.** A wireframe drawn over the surface it outlines shares the exact
  depth of the faces meeting at that edge, so the outline z-fights: dashed, and
  crawling as the camera moves. Depth bias is the textbook fix and the pipeline
  state was accepted without complaint -- but it is specified for polygons, and
  a line list is not one, so it is silently ignored. The offset that works is in
  `mesh_line.frag`, which writes `SV_Depth` and moves the fragment itself. That
  costs the line pipeline its early-z, which for a few thousand line pixels is
  not worth measuring
- **`Model_Part` grew a `topology`, and `draw_model` picks the pipeline per
  part.** Lines and triangles are the same vertex layout and the same vertex
  shader, so the only thing that differs is the pipeline -- and a part is the
  thing that knows which it is. A loaded file could hold both
- **`draw_bounds_wires(lower, upper, colour)` was added** alongside the
  centre-and-size form, because that is the shape `b3.Shape_GetAABB` and
  `b3.Body_ComputeAABB` report. Two plain vectors, so Matchbox still knows
  nothing about Box3D (D7)
- the generated shapes are built on first use and shared, so a hundred cubes are
  a hundred draws of one vertex buffer. A 2D game allocates none of them

**Milestone A. `CoffeeGame` is rebuilt on Matchbox.** It needs cubes, wireframes,
a grid, a first-person camera, a crosshair and text -- all of which now exist --
plus `vendor:box3d`, which it already calls directly and which Matchbox does not
touch. Nothing in stages 4 to 6 is required for it.

The port to check the design against: `rlgl.PushMatrix`/`Rotatef` around the
held cube becomes a `Transform` with a quaternion, which is the one place
`CoffeeGame` reaches under raylib's API and the one place worth confirming the
new API is no worse.

**Done.** `games/CoffeeGameMatchbox/` runs, beside the raylib original rather
than over it. Verified by driving it: walking forward for three and a half
seconds presses the player against the maroon slab instead of through it, which
is Box3D resolving collisions against a camera Matchbox never moves.

- **The rlgl reach was worth checking and came out better than expected.**
  `b3.Quat` is `quaternion128`, which is what `Transform.rotation` and
  `draw_cube` take -- so a body's orientation goes from the solver to the draw
  call with no conversion at all. raylib needed a matrix push, a `Rotatef` in
  degrees off `GetAxisAngle`, and a pop. `draw_cube` grew an optional `rotation`
  for this, defaulted to the identity so nothing else changed
- **D7 held up.** Not one line of the physics moved. The world, the bodies, the
  capsule, the ray casts and the kinematic hand are the original's, character
  for character. What was ported was raylib's renderer and raylib's input, which
  is the whole claim the decision makes
- **One latent bug fell out.** The original built its strafe vector as
  `cross(up, forward)`, which points left, and then subtracted it for D -- two
  sign errors that cancelled. `walk_direction` uses the conventional right
  vector, so the behaviour is the same with less arithmetic
- not carried over: `MSAA_4X_HINT`, which Matchbox does not have. Nothing in the
  game depends on it

### Stage 4 -- Models from files

The package was checked rather than assumed: `matchbox/gltf2` compiles as it
stands, handles `.gltf` and `.glb`, and exposes `parse(bytes)` separately from
its `load_from_file`, which is the one that would reach for `core:os`.

The assets were checked too, and they are the easy case.
`campfireV1.gltf` and `cube.gltf` embed their buffers *and* their PNG textures as
base64 data URIs, so nothing resolves an external file and the `core:os` path in
`uri_parse` is never taken. Every primitive is indexed triangles carrying exactly
`POSITION`, `NORMAL`, `TEXCOORD_0` -- which is `Vertex3D` with nothing left over
and nothing missing.

**Work**

- `load_model(path) -> Model`: `read_entire_file` into `gltf2.parse`, so it works
  from inside an Android apk like everything else does
- materials: base colour texture and factor. The texture is an embedded PNG,
  decoded by the stb_image that `image.odin` already uses and uploaded on the
  existing `upload_texture` path
- normals generated when a file omits them -- none of these do, but the loader
  should not assume the next one won't
- the model's local bounds, as a field filled in at load. Not a collision
  feature: it is how a game sizes a `MakeBoxHull` for the model it just loaded,
  and what `draw_box_wires` is pointed at (D7)
- `destroy_model`, added to the `destroy` proc group
- textured lit-less fragment shader, so a model is visible before stage 5

**Done when** `examples/model` loads `campfireV1.gltf` and draws it with its
bounding box.

**Done.** All four `.gltf` files load, textured and assembled: campfire 1 part,
cube 1, pot 2, stove 11. The example seats each on the ground off its own
`bounds_min`, which is the bounds doing real work rather than being drawn for
show.

**Two bugs, and the first one is in the vendored package.**

- **`gltf2`'s base64 decoder returned nothing, always.** `uri_parse` read
  `if data, err := base64.decode(...); err != nil { return uri }` -- and that
  `if` declares a *second* `data` scoped to itself, so a decode that succeeded
  returned the outer one, still nil. Every embedded buffer and every embedded
  texture came back as zero bytes, silently, because an empty slice is a
  perfectly valid `Uri`. Since every asset here embeds everything, nothing
  would ever have loaded. **This is a patch to vendored code and a refresh of
  the package will undo it** -- it is marked `MATCHBOX PATCH` in
  `gltf2/gltf.odin` so a diff will find it
- **`filepath.dir` returns a slice of its argument, not an allocation.** The
  loader deleted it, which frees a pointer into the middle of somebody else's
  string, and the heap corruption surfaced three calls later with a status code
  and no message. Worth remembering as a shape: the crash was in teardown, the
  cause was a borrowed slice treated as owned

**Design notes:**

- **The accessors are read here, not with `gltf2.buffer_slice`.** That helper
  asserts on any buffer view declaring a `byteStride`, and every one of these
  files declares one -- Blockbench writes a stride of 12 on tightly packed vec3
  data, which is redundant and legal. So the helper cannot read the models it
  exists for. Reading the bytes directly is forty lines and handles interleaved
  data as a side effect
- **Node transforms are baked into the vertices at load.** The campfire's mesh
  hangs off a node rotated ninety degrees inside another that moves it, and the
  stove is nine meshes across a tree. Flattening at load means a part is one
  buffer and one draw, and a Model needs no arranging afterwards
- textures are uploaded once and shared between the parts that name them, and
  bound with the nearest-neighbour sampler sprites use -- every file asks for
  `magFilter` 9728, because they are pixel art
- `Industrial_exterior_v2.glb`, the risk register's unknown, is **still
  unopened**. The four small files are the ones proven

### Stage 5 -- Lights and fog

`lighting.vs` and `lighting.fs` ported to HLSL per D3.

**Work**

- `Light :: struct { kind: enum { POINT, DIRECTIONAL }, position, target: [3]f32,
  color: [4]f32, enabled: bool }`
- four lights, which is what `rlights.odin` allows and more than either game
  uses. A fixed-size fragment uniform block, so no storage buffers and no
  bindless
- fog: colour, start and end, matching the existing uniforms
- `set_lights`, `set_fog`, and the view position pushed from the active camera
  rather than by the game

**Done when** `examples/lighting` reproduces the campfire: a point light whose
colour and position wobble per frame, over a fogged dark scene.

**Done.** `examples/lighting` is that scene, with PsxGame's flicker copied line
for line and its constants -- attenuation curve, specular exponent, ambient over
ten, gamma before fog -- ported unchanged.

**The decision that was not in the plan: lighting is opt-in.**

Making every 3D draw lit is what the stage says to do, and doing it literally
turns every scene written in stages 1 to 4 black, `CoffeeGame` included -- no
lights configured, so nothing reflects any. So a scene with no lights set keeps
the fixed shading it always had, and the real model takes over the moment
`set_lights` is called with one. `clear_lights` goes back. Verified by
re-running `examples/primitives`, which is pixel-identical to its stage 3 shot.

Worth knowing: *no lights at all* and *four disabled lights* deliberately mean
different things. The first is the fallback; the second is a scene lit by
nothing, which is black, and is a legitimate thing to ask for.

**The rest:**

- **Every member of the uniform block is a `[4]f32`, including the ones that
  are logically a position or a colour.** This is the packing hazard the risk
  register named, met head on: HLSL will not let a vector straddle a 16-byte
  boundary and pads silently to avoid it, so a `float3` followed by a `float` is
  16 bytes or 32 depending on rules that are easy to misremember, and the
  failure is wrong lighting rather than an error. All-`float4` makes the two
  sides agree by construction, and `#assert(size_of(Lighting_Data) == 272)`
  confirms it. `position.w` carries enabled, `target.w` carries the kind
- **Two fragment uniform slots.** Slot 0 is the per-draw tint, slot 1 is the
  lighting, pushed once per pass. Both lit shaders declare
  `num_uniform_buffers = 2`
- **dxc resolves `#include`, and `build_shaders.bat` only compiles `*.vert.hlsl`
  and `*.frag.hlsl`.** So the model lives in `lighting.hlsli`, included by the
  flat and textured shaders and compiled as neither -- rather than the same
  fifty lines maintained twice
- the view position comes from the camera `begin_drawing_3d` was given, not from
  the game. It is the pass's business and a game should not have to remember to
  hand it over for specular and fog to be right

### Stage 6 -- Render targets and post-processing

**Work**

- `Render_Target`: a colour texture with `{.COLOR_TARGET, .SAMPLER}` in the
  swapchain format (D5), plus its own depth texture
- `begin_drawing_target(&target)` / `end_drawing_target()`, following the same
  pass-switching rules as D1 and the same naming as D10
- `psx.frag.hlsl` and `vhs.frag.hlsl`, drawn as one full-screen quad (D4).
  PSX needs a `resolution` uniform, VHS needs `resolution` and `time`
- `draw_post(target, effect, params)` where `effect` is `.NONE`, `.PSX` or
  `.VHS`

**Stage 6 done.** `examples/post` runs the campfire scene through all three:
none, VHS and PSX, switched live, with the HUD drawn after the effect so it
stays sharp -- which is what PsxGame does and is half of why the look reads.

**What it took, and what it did not:**

- **D4 paid off exactly as predicted.** An effect is a fragment shader and
  nothing else. The quad vertex shader every 2D draw already uses puts a
  rectangle anywhere at any size, so a full-screen pass is that rectangle at the
  size of the window. `draw_post` is thirty lines and most of them pick a
  sampler
- **The samplers differ per effect, which is not a detail.** PSX samples nearest
  -- snapping a uv to the middle of a coarse cell has to pick one texel, and a
  linear blend of four would undo the whole effect. VHS samples linear, because
  it reads at arbitrary offsets for the barrel curve, the chroma taps and the
  ghost, and nearest makes every one of them stair-step
- **No flip.** raylib needs a negative source height to draw a render texture
  the right way up, because an OpenGL framebuffer is bottom-up. SDL3_GPU is
  top-down like the swapchain, so what was rendered is what is sampled
- **`screen_dims` had to learn about targets.** It reported the window, which is
  the divisor the 2D vertex shader uses -- so 2D drawn into a target of another
  size landed off the edge of it. It now reports whichever is bound
- **A passthrough effect needs its own shader**, though the sprite shader looks
  like it would do. Its uniform block is a tint and a desaturate; post-processing
  pushes a resolution, a grid and a time. Two blocks of the same size and
  different meaning, which is the mix-up that reads as a picture in the wrong
  colours. Caught before it ran, by writing down what the block meant

**Milestone B. `PsxGame` is rebuilt on Matchbox.** Scene into a target, target
through an effect, UI drawn crisp on top afterwards -- which is exactly the order
its main loop already has.

The rendering side is a translation. The collision side is not: per D7 the four
hand-rolled AABB routines come out and a Box3D world goes in, modelled on the one
`CoffeeGame` will already have working by then. That is game-side work and none of
it lands in Matchbox, but it is the part of this milestone that is a rewrite
rather than a port, and it is worth budgeting for as such.

**Done.** `games/PsxGameMatchbox/` runs at 60fps: models, the flickering
campfire, fog, the render target, all three filters, the HUD unfiltered on top,
Box3D stopping the player against a crate, and the look ray naming what the
crosshair is on.

**Nothing landed in Matchbox for this milestone.** Every framework piece it
needed already existed by the end of stage 6, which is the plan working.

**Two things the game had to learn, both about the physics rather than the
renderer:**

- **A look ray starting at the camera starts inside the player's own capsule.**
  Cast with no filter, it can return that capsule before it reaches anything
  worth naming, and the readout stays silent while looking as though the ray is
  broken. Collision categories fix it -- the player is one category, the world
  is another, and the look ray masks to the world. `CoffeeGame` already does
  this for the same reason, which is the sort of thing that is obvious in
  hindsight and invisible in advance
- **raylib's `GetRayCollisionBox` takes a ray, not a segment**, so the original
  reports the first thing along the line however distant. `World_CastRayClosest`
  wants a translation, so "unbounded" has to become a number. Picking a short
  one first made near things work and far things silently not

**And one deliberate departure:** the original calls `GetRayCollisionBox` but has
everything inside the `if hit` commented out, so looking at something does
nothing. The port wires it up, because with a solver it is one call and an inert
feature cannot be verified.

## Risk register

**The projection convention (D2).** Highest risk in the plan, because it fails as
a rendering artefact rather than an error. Mitigated by putting it in stage 1
behind a test that shows it: a cube close to the near plane must stay visible.

**Winding and culling.** glTF is counter-clockwise front-facing. The 2D shader's
y negation flips winding, which is why `create_pipeline` sets `cull_mode = .NONE`
and says so. 3D wants back-face culling on, so the front face has to be settled
deliberately in stage 1 and generated primitives made to match.

**Uniform block packing.** The same hazard the SDL3 migration hit, and the reason
every uniform struct in `types.odin` carries its size in a comment. A `matrix[4,4]f32`
is 64 bytes and safe; the light array in stage 5 is where a `float3` will straddle
a 16-byte boundary and produce quietly wrong lighting. Every new block gets a size
comment and an assert in `init`, as the existing ones do.

**Matrix majorness.** The 3D counterpart of the packing hazard, and it fails the
same quiet way. HLSL packs `float4x4` in a cbuffer column-major by default;
Odin's `matrix[4,4]f32` is column-major too, so `mul(m, v)` should line up
without a `pack_matrix` pragma or `-Zpr`. Should. It is one `#pragma` away from
being transposed on one backend and not the other, so stage 1 confirms it on both
SPIR-V and DXIL rather than on whichever machine was handy.

**Depth format availability.** `D24_UNORM_S8_UINT` is not guaranteed. Query, fall
back, and do not assume the desktop answer holds on Android.

**Android.** The 3D path should stay portable -- SDL3_GPU on Vulkan is what the
`ui` example already runs on a phone -- but nothing here has been tried there.
Worth one check at Milestone A rather than a stage of its own, since finding out
early costs nothing and finding out late costs a redesign.

**A framework that quietly grows a physics engine.** The line in *The line
Matchbox draws* holds only if it is defended at the moment it is inconvenient --
which will be some afternoon in stage 4 when adding one overlap test is faster
than wiring up a body. `boxes_overlap` is how these things start. Matchbox
importing `vendor:box3d` is how you know it already happened.

**Scope creep through `Model`.** glTF describes far more than either game uses.
Load what is needed -- positions, normals, UVs, indices, base colour -- and let
the rest fail loudly rather than half-working.

The four small `.gltf` files are one mesh and one material each and are checked.
`Industrial_exterior_v2.glb` is 1.7MB of binary glTF and is **not** -- it is the
one asset likely to have several meshes, several materials and a texture layout
worth looking at before stage 4 is scoped.

### Stage 7 -- Skeletal animation

Started by the thing the "Not doing" list said would start it: a VRoid character
with a Mesh2Motion walk cycle, in a game that wanted it to walk.

**Work**

- `Vertex3D_Skinned` and a `.SKINNED` vertex layout -- the same three attributes
  plus four joints and four weights, 56 bytes against Vertex3D's 32
- `mesh_skinned.vert.hlsl`: `mesh.vert` with a weighted sum of joint matrices in
  front of it, and a second uniform block holding the palette
- two more pipelines, flat and textured, because a skinned part still has or has
  not got a texture
- `Skeleton`, `Model_Skin`, `Model_Animation`, `Animation_Track` -- what comes
  out of the file and never changes
- `Animator`, `create_animator`, `play_animation`, `update_animator` -- one
  character's playback, allocated per character rather than per model
- `build_skeleton` and `build_animations` in `model_skin_load.odin`, plus the
  accessor readers only a character needs: keyframe times, quaternions, inverse
  bind matrices, joint indices and weights
- `draw_model` grew an `animator` argument, defaulted to nil

**Done when** a loaded `.glb` character walks its own clip.

**Done, and checked against an independent implementation rather than by
looking at it.** The joint globals, the inverse bind matrices and a sampled
palette were computed a second time in numpy straight from the glb, and matched
Matchbox to four decimal places -- f32 against f64, which is the whole of the
difference. 150 frames ran under Vulkan validation with the skinned pipeline
bound and nothing reported.

**What it changed:**

- **A skinned primitive does not get the node transform baked into it**, which
  is the one place the stage 4 loader had to be undone rather than extended.
  Skinned vertices live in the skin's space and the joint matrices are what put
  them anywhere; baking the arrangement in as well applies it twice. glTF says
  the node's transform is not applied to a skinned mesh, and `animator_resolve`
  divides it back out in full -- the `inverse(mesh node global)` term, which is
  the identity in most files and was in this one, but is a matrix inverse per
  part per frame rather than a guess
- **The rest pose is not the bind pose, and assuming otherwise cost an hour.**
  The obvious check for skinning -- at the bind pose every joint matrix should
  come out as the identity -- failed by 2.18 on this file, which looks exactly
  like transposed matrices or a joint list indexed by the wrong number. It was
  neither: glTF's node transforms are just *a* pose, and only the inverse bind
  matrices define the bind one. CPU-skinning the file at its own rest pose moved
  vertices 0.07 units on average, which is a small offset and not a mangled
  character. The test's premise was wrong, not the code, and the numpy
  comparison is what settled it
- **Two vertex types rather than two more fields on one.** Every cube, plane,
  sphere and unskinned model in every game would otherwise carry twenty-four
  bytes of zeroes a vertex for a feature it does not use. The line pipeline set
  the precedent: a part knows what it is and the draw call picks accordingly
- **The palette is a fixed 128-matrix uniform block, and the whole thing is
  pushed every time.** 8KB, inside the 16KB Vulkan guarantees, and well past
  what a rig needs -- the VRoid skeleton is 66 joints including hair and skirt
  bones. Pushing only the used entries would leave whatever the previous draw
  wrote in the rest, which is a character stretched across the map the first
  time two models with different joint counts share a frame
- **`Animator` is per character, not per model.** A `Model` is one upload on the
  GPU and two goblins share it; what differs is where each of them is in its
  clip. Same reasoning as `draw_model` taking a `Transform` rather than storing
  one, and the same reasoning that put yaw and pitch in the game rather than on
  `Camera3D`
- **Morph targets are still skipped**, which is the patch that made this file
  load at all. Blend shapes need a shader that interpolates between them and are
  a separate feature from this one
- **`STEP` is not a rounding error.** 45 of this clip's 67 channels are stepped,
  which is Mesh2Motion baking rather than anything unusual, and a sampler that
  quietly treated them as linear would look smoother and be wrong
- no example in the repository, because there is no character asset in it to
  animate and a 35MB VRoid export is not one to add. The two-call shape is
  `create_animator` beside `load_model` and `update_animator` beside the rest of
  the frame

**Not done, and each is its own stage:** blending between two clips, which is
what a walk that eases into a run needs; root motion, where the clip moves the
character rather than the game doing it; and attaching something to a joint,
which is one lookup into `Animator.globals` away and wants an API rather than a
convention.

### Stage 8 -- Skyboxes

Two formats, because sky packs ship as both and neither converts to the other
without loss: a 2:1 equirectangular **panorama**, and six square faces packed as
a 4x3 **cross**.

**Work**

- `Skybox`, `load_skybox_panorama`, `load_skybox_cubemap`, `draw_skybox`
- `skybox.vert.hlsl`, which reads no geometry at all -- one screen-covering
  triangle built from `SV_VertexID`, and a `Vertex_Layout.NONE` for a pipeline
  with zero vertex buffers
- `skybox_panorama.frag.hlsl` and `skybox_cubemap.frag.hlsl`
- `create_gpu_cube_texture` and `upload_texture_layer`, for a `.CUBE` texture
  filled a face at a time
- `depth_ignore` on `create_pipeline`: the pass has a depth buffer, this
  pipeline declares it and neither tests nor writes it

**Done when** both formats draw behind a scene and stay put as the camera moves.

**Done, and checked by simulating the hardware rather than by looking at it.**
The cube face selection rules were reimplemented in numpy over the real file:
straight up lands on `+Y` and comes back sky, straight down lands on `-Y` and
comes back ground, a full turn round the horizon has a largest neighbouring-degree
jump of 3.0 out of 255, and a point to the viewer's right lands right of image
centre. The panorama was checked the same way, plus the structural test that
matters for an equirectangular image: its top and bottom rows vary by 0.37 and
1.93 across their whole width, which is what a pole looks like and what proves
`v = 0` is the zenith.

**What it changed:**

- **A sky is not geometry, and building it as geometry is the trap.** No dome,
  no very large cube, no transform. One triangle, and a direction per pixel --
  which is why `draw_skybox` cannot be given a position and why walking does not
  move it
- **The camera basis is passed already scaled, rather than a matrix inverted in
  the shader.** `right * tan(fov/2) * aspect`, `up * tan(fov/2)`, `forward`, and
  the ray is their sum. Cheaper than an inverse view-projection and far easier
  to check on paper
- **Cube maps are sampled left-handed, and Matchbox's world is not.** The one
  place Direct3D's convention survived into every API since. Looking along +z,
  Matchbox's camera right is -x where the cube map's +Z face puts +x to the
  right of the image, so the sky comes out mirrored unless x is negated at the
  sample. Done in the shader rather than by swapping faces at upload, so what
  the loader slices matches the labels the cross is drawn with
- **`Vertex_Layout.NONE` and `depth_ignore` are both new pipeline states.** The
  first because a shader that invents its own vertices needs no buffer; the
  second because `depth = false` means *the pass has no depth attachment*, which
  is a different claim and one a pipeline used inside the 3D pass cannot make
- **A one-line bug meant Matchbox had never logged anything.** `init` guarded
  its console logger with `context.logger.procedure == nil`, and Odin's default
  context does not leave that nil -- it fills it with `nil_logger_proc`, a real
  procedure that discards. So the guard was always false, the logger was never
  created, and every `log.error` in the package went nowhere, including the ones
  the guard's own comment was written to protect. `core:log` makes the same
  two-part test internally. Found because the new loaders' guards fired
  correctly and said nothing

**Not done:** mip maps on the sky, which a panorama wants at grazing angles and
which needs the seam handled; and reading the sky as an ambient light, which is
what an engine does with a cube map once it has one.

## Not doing, and what each would take

- ~~**Skeletal animation.**~~ **Done** -- a game wanted a character to walk,
  which is what this entry said would start it. See *Stage 7* below
- **Shadows.** A depth-only pass per light plus a shadow sampler in the lit
  shader. Neither game has shadows now
- **MSAA.** `CoffeeGame` asks for `MSAA_4X_HINT`. SDL3 supports it through
  `sample_count` and a resolve target, but it touches every pipeline, and PSX
  wants aliasing on purpose. Revisit at Milestone A if the cubes look bad
- **A shader API for games.** D3 rules it out for now. It would be
  `load_shader` over compiled blobs plus a way to declare a uniform block, and
  everything already goes through `create_pipeline`, so it stays possible
- **Instancing.** `DrawGPUIndexedPrimitives` already takes an instance count.
  Worth doing the day something draws a thousand of one mesh
- **Collision, ray casting, physics.** Box3D's, per D7 and the section above it.
  Not deferred -- declined. The nearest thing Matchbox will own is a model
  knowing its own dimensions, which is what a game measures a collider from
